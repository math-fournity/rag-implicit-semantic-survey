三大主流RAG框架的默认提示词模板揭示了截然不同的设计哲学：**LlamaIndex强调上下文受限与迭代精炼**，**LangChain追求模块化与Hub生态**，**GraphRAG则采用结构化抽取与多阶段推理**。本报告通过源代码逆向工程，完整还原这些框架的核心提示词模板，识别设计模式，并提供跨框架对比分析。

## 第58章：LlamaIndex提示词模板体系

LlamaIndex的提示词设计围绕一个核心原则展开——**"基于上下文而非先验知识"（context-grounded answering）**。几乎所有默认提示词都包含明确指令，禁止模型使用训练数据中的知识，强制其仅依赖检索到的上下文生成答案。

### 摘要生成提示词的递归策略

**TreeSummarize**采用自底向上的递归摘要策略，其核心提示词位于`llama_index/core/prompts/default_prompts.py`：

```
Context information from multiple sources is below.
---------------------
{context_str}
---------------------
Given the information from multiple sources and not prior knowledge, answer the query.
Query: {query_str}
Answer:
```

这个看似简单的模板实际上是TreeSummarize算法的构建基块。系统将多个文档块的摘要递归合并，每层都使用相同的模板，直到生成最终的统一答案。变量`{context_str}`在不同层级承载不同内容——底层是原始文档块，上层则是子节点的摘要结果。

**Refine摘要模式**体现了LlamaIndex的"保守策略"设计哲学。当新上下文与现有答案冲突时，模板明确指示模型"宁可保留原答案"：

```
The original query is as follows: {query_str}
We have provided an existing answer: {existing_answer}
We have the opportunity to refine the existing answer (only if needed) with some more context below.
------------
{context_msg}
------------
Given the new context, refine the original answer to better answer the query. 
If the context isn't useful, return the original answer.
Refined Answer:
```

Chat版本（`CHAT_REFINE_PROMPT`）更进一步，将行为模式简化为二元选择："**Rewrite**使用新上下文重写，或**Repeat**保留原答案"。这种设计有效降低了模型在迭代过程中引入幻觉的风险。

### 问答提示词的角色约束

LlamaIndex的QA提示词在Chat格式中引入了显式的角色约束规则。系统消息定义了一个"全球受信任的专家问答系统"角色，并附带明确的行为禁令：

```python
ChatMessage(
    role=MessageRole.SYSTEM,
    content=(
        "You are an expert Q&A system that is trusted around the world.\n"
        "Always answer the query using the provided context information, "
        "and not prior knowledge.\n"
        "Some rules to follow:\n"
        "1. Never directly reference the given context in your answer.\n"
        "2. Avoid statements like 'Based on the context, ...' or "
        "'The context information ...' or anything along those lines."
    ),
)
```

**CondenseQuestion提示词**（位于`llama_index/core/chat_engine/condense_question.py`）解决了多轮对话中的指代消解问题。它将对话历史和后续问题压缩为独立的查询：

```
Given a conversation (between Human and Assistant) and a follow up message from Human,
rewrite the message to be a standalone question that captures all relevant context 
from the conversation.

<Chat History>
{chat_history}
<Follow Up Message>
{question}
<Standalone question>
```

### 结构化输出的Schema驱动模式

LlamaIndex对结构化输出采用**Schema驱动生成**模式。`OpenAIPydanticProgram`利用函数调用能力直接绑定Pydantic模型，而非函数调用LLM则需要显式注入JSON Schema：

```python
prompt_template_str = (
    "Your response should be according to the following json schema: \n"
    "{json_schema}\n"
    "Generate an example album, with an artist and a list of songs. "
    "Using the movie {movie_name} as inspiration."
)
```

`RichPromptTemplate`引入了Jinja2语法支持，允许更复杂的模板逻辑，包括循环、条件和过滤器。`{% chat role="system" %}`块可以直接定义消息角色，`{{ variable | image }}`过滤器支持多模态内容处理。

### 评估提示词的Few-shot设计

**Faithfulness评估提示词**展示了LlamaIndex对Few-shot学习的典型应用。它提供了正反两个示例来校准模型的判断标准：

```
Please tell if a given piece of information is supported by the context.
You need to answer with either YES or NO.

Information: Apple pie is generally double-crusted.
Context: An apple pie is a fruit pie... It is generally double-crusted...
Answer: YES

Information: Apple pies tastes bad.
Context: An apple pie is a fruit pie...
Answer: NO

Information: {query_str}
Context: {context_str}
Answer:
```

Refine版评估模板采用"once YES, always YES"的累积判断逻辑，确保多轮评估不会因上下文切换而翻转已确认的结论。

### 提示词自定义机制

`PromptTemplate`基类定义了核心扩展接口。关键属性包括`template_vars`（模板变量列表）、`output_parser`（输出解析器）、`template_var_mappings`（变量重映射）和`function_mappings`（动态函数注入）。

**PromptSelector**机制实现了模型感知的提示词选择。`SelectorPromptTemplate`根据LLM类型（chat vs completion）自动切换对应格式：

```python
SelectorPromptTemplate(
    default_template=PromptTemplate(...),
    conditionals=[
        (is_chat_model, ChatPromptTemplate(...)),
    ]
)
```

运行时自定义有三种方式：直接传参替换、`update_prompts()`方法更新、或通过`get_prompts()`查看后修改。LlamaIndex目前不提供内置多语言支持，用户需手动翻译并替换模板。

## 第59章：LangChain与LangGraph提示词体系

LangChain的提示词设计遵循**模块化与可组合性**原则，通过Hub生态实现版本管理和社区共享。LangGraph则代表了设计范式的转变——**从隐式默认到显式定义**。

### ReAct Agent的经典推理循环

ReAct Agent提示词（`hwchase17/react`）是LangChain最具影响力的模板之一，定义了"思考-行动-观察"的推理范式：

```
Answer the following questions as best you can. You have access to the following tools:

{tools}

Use the following format:

Question: the input question you must answer
Thought: you should always think about what to do
Action: the action to take, should be one of [{tool_names}]
Action Input: the input to the action
Observation: the result of the action
... (this Thought/Action/Action Input/Observation can repeat N times)
Thought: I now know the final answer
Final Answer: the final answer to the original input question

Begin!

Question: {input}
Thought:{agent_scratchpad}
```

四个关键变量驱动整个循环：`{tools}`提供工具描述，`{tool_names}`约束行动空间，`{input}`接收用户问题，`{agent_scratchpad}`累积中间推理步骤。LangGraph的`create_react_agent`则**完全放弃默认提示词**，要求用户通过`prompt`参数显式提供。

### Router提示词的分类决策

**MULTI_PROMPT_ROUTER_TEMPLATE**实现了基于语义的提示词路由：

```
Given a raw text input to a language model select the model prompt best suited 
for the input. You will be given the names of the available prompts and a 
description of what the prompt is best suited for.

<< CANDIDATE PROMPTS >>
{destinations}

<< INPUT >>
{input}

<< OUTPUT >>
```

现代LangGraph实践倾向于使用结构化输出替代字符串解析：

```python
class RouteQuery(TypedDict):
    """Route query to destination."""
    destination: Literal["animal", "vegetable"]

route_chain = route_prompt | llm.with_structured_output(RouteQuery)
```

### Memory提示词的实体跟踪

**ConversationSummaryMemory**使用渐进式摘要策略，每次只处理新增对话：

```
Progressively summarize the lines of conversation provided, adding onto 
the previous summary returning a new summary.

Current summary:
{summary}

New lines of conversation:
{new_lines}

New summary:
```

**EntityMemory**的实体提取提示词展示了更复杂的Few-shot设计。它明确处理指代消解场景（"him"指向前文定义的实体），并通过详细示例演示了期望的输出格式——逗号分隔的专有名词列表或"NONE"。

### RAG提示词的四种组合模式

LangChain提供了四种文档组合策略，每种对应不同的提示词模板：

**Stuff模式**最简单直接，将所有上下文拼接后一次性处理：
```
Use the following pieces of context to answer the question at the end. 
If you don't know the answer, just say that you don't know, don't try to make up an answer.

{context}

Question: {question}
Helpful Answer:
```

**Map-Reduce模式**采用两阶段设计。Map阶段提取相关文本片段，Reduce阶段综合生成最终答案。Reduce提示词包含完整示例来演示期望的输出格式。

**Refine模式**与LlamaIndex的设计类似，通过迭代精炼增量更新答案。但LangChain的措辞更强调"必须提供响应"，而LlamaIndex则倾向于"保守保留"。

**Map-Rerank模式**引入了自信度校准机制，要求模型同时输出答案和0-100分的评分：
```
In addition to giving an answer, also return a score of how fully it answered 
the user's question...

How to determine the score:
- Higher is a better answer
- If you do not know the answer based on the context, that should be a score of 0
- Don't be overconfident!
```

### Hub生态的标准化提示词

**`rlm/rag-prompt`**是Hub上使用最广泛的RAG提示词，针对简洁性优化：
```
You are an assistant for question-answering tasks. Use the following pieces of 
retrieved context to answer the question. If you don't know the answer, just say 
that you don't know. Use three sentences maximum and keep the answer concise.
Question: {question} 
Context: {context} 
Answer:
```

Hub支持版本锁定（`hub.pull("rlm/rag-prompt:50442af1")`）和模型特定变体（`rlm/rag-prompt-llama3`、`rlm/rag-prompt-mistral`）。

### 结构化输出的演进

LangChain的结构化输出经历了从`OutputParser`到`with_structured_output`的演进。旧模式需要手动注入格式指令：

```python
format_instructions = parser.get_format_instructions()
# 生成: "The output should be formatted as a JSON instance that conforms to..."
```

**OutputFixingParser**提供了错误自修复能力，当解析失败时使用专门的修复提示词：
```
Instructions: {instructions}
Completion: {completion}
Above, the Completion did not satisfy the constraints given in the Instructions.
Error: {error}
Please try again...
```

新的`with_structured_output`模式直接绑定Schema，无需额外格式指令，代表了LangChain推荐的最佳实践。

## 第60章：GraphRAG提示词逆向工程

微软GraphRAG的提示词设计体现了**结构化信息抽取**和**多阶段推理**的独特方法论。与LlamaIndex和LangChain的问答导向不同，GraphRAG的核心提示词专注于知识图谱的构建与查询。

### 实体抽取的结构化格式

**entity_extraction提示词**（位于`graphrag/prompts/index/extract_graph.py`）定义了严格的输出格式规范：

```
-Goal-
Given a text document that is potentially relevant to this activity and a list of 
entity types, identify all entities of those types from the text and all relationships 
among the identified entities.

-Steps-
1. Identify all entities. For each identified entity, extract the following information:
- entity_name: Name of the entity, capitalized
- entity_type: One of the following types: [{entity_types}]
- entity_description: Comprehensive description of the entity's attributes and activities
Format each entity as ("entity"{tuple_delimiter}<entity_name>{tuple_delimiter}<entity_type>{tuple_delimiter}<entity_description>)

2. From the entities identified in step 1, identify all pairs of (source_entity, target_entity) 
that are *clearly related* to each other.
...
Format each relationship as ("relationship"{tuple_delimiter}<source_entity>{tuple_delimiter}<target_entity>{tuple_delimiter}<relationship_description>{tuple_delimiter}<relationship_strength>)
```

**关键设计特征**包括：自定义分隔符系统（`{tuple_delimiter}`、`{record_delimiter}`）确保输出可靠解析；关系强度以数值分数（1-10）表示，支持图上的加权分析；Few-shot示例使用虚构的"Verdantis"场景，避免与真实实体混淆。

**循环抽取机制（Gleaning）**通过多轮提示确保抽取完整性：
```
CONTINUE_PROMPT = "MANY entities and relationships were missed in the last extraction. 
Remember to ONLY emit entities that match any of the previously extracted types. 
Add them below using the same format:\n"

LOOP_PROMPT = "It appears some entities and relationships may have still been missed. 
Answer YES | NO if there are still entities that need to be added.\n"
```

### 声明抽取的时间与置信度建模

**claim_extraction提示词**扩展了实体抽取范式，增加了时间维度和置信度判断：

```
For each claim, extract the following information:
- Subject: name of the entity that is subject of the claim
- Object: name of the entity that is object of the claim
- Claim Type: overall category of the claim
- Claim Status: TRUE, FALSE, or SUSPECTED
- Claim Description: Detailed description explaining the reasoning
- Claim Date: Period (start_date, end_date) when the claim was made (ISO-8601 format)
- Claim Source Text: List of all quotes from the original text relevant to the claim
```

三元组状态设计（TRUE/FALSE/SUSPECTED）支持不确定性建模，这在法律、金融等需要区分已确认事实与疑似信息的领域尤为重要。

### 社区摘要的层级策略

**summarize_descriptions提示词**处理同一实体的多个描述片段，要求模型解决潜在矛盾并生成统一摘要：

```
You are a helpful assistant responsible for generating a comprehensive summary 
of the data provided below.
Given one or more entities, and a list of descriptions, all related to the same 
entity or group of entities.
Please concatenate all of these into a single, comprehensive description. 
Make sure to include information collected from all the descriptions.
If the provided descriptions are contradictory, please resolve the contradictions 
and provide a single, coherent summary.
```

**社区报告提示词**要求生成结构化的JSON输出，包含标题、摘要、影响严重性评分（0-10）和详细发现列表。**Grounding Rules**是GraphRAG的独特设计，强制模型引用数据来源：

```
Points supported by data should list their data references as follows:
"This is an example sentence supported by multiple data references 
[Data: <dataset name> (record ids); <dataset name> (record ids)]."

Do not list more than 5 record ids in a single reference. Instead, list the top 5 
most relevant record ids and add "+more" to indicate that there are more.
```

### 查询阶段的Local/Global/DRIFT三模式

**Local Search提示词**面向精确的实体级查询，直接使用索引数据表：

```
---Role---
You are a helpful assistant responding to questions about data in the tables provided.

---Goal---
Generate a response of the target length and format that responds to the user's question, 
summarizing all information in the input data tables appropriate for the response length 
and format, and incorporating any relevant general knowledge.
```

**Global Search采用Map-Reduce架构**。Map阶段从各社区报告中提取关键点并评分（0-100），Reduce阶段按重要性降序合并这些分析师报告。这种设计使GraphRAG能够回答需要综合多个社区知识的宏观问题。

**DRIFT Search**（Dynamic Reasoning and Inference with Flexible Traversal）是2024年引入的新模式，结合了Local和Global搜索的优势。其Primer阶段提示词要求模型提供中间答案、相关性评分和后续查询建议：

```
You will begin your reasoning looking at a summary of the content of the most 
relevant communities and will provide:

1. score: How well the intermediate answer addresses the query (0-100)
2. intermediate_answer: This answer should match the level of detail and length 
   found in the community summaries. Exactly 2000 characters long.
3. follow_up_queries: A list of follow-up queries that could be asked to further 
   explore the topic.
```

### 提示词自动调优实验

GraphRAG提供了CLI级别的提示词自动调优功能：

```bash
graphrag prompt-tune --root /path/to/project \
  --domain "environmental news" \
  --selection-method random \
  --limit 10 \
  --discover-entity-types \
  --output /path/to/output
```

关键参数包括：`--domain`指定数据领域以生成领域特定示例；`--selection-method`控制训练文档选择策略（random/top/all/auto）；`--discover-entity-types`允许模型自动发现实体类型而非使用预定义列表。

调优的核心机会在于**Few-shot示例的领域定制**。默认的Verdantis示例适用于通用场景，但特定领域（生物医学、法律、金融）需要替换为领域相关的实体和关系示例。

## 跨框架提示词设计模式对比

| 设计维度 | LlamaIndex | LangChain | GraphRAG |
|---------|------------|-----------|----------|
| **核心原则** | 上下文受限回答 | 模块化可组合 | 结构化信息抽取 |
| **默认提示词** | 完整内置 | 内置+Hub生态 | 完整内置+可调优 |
| **Few-shot使用** | 评估类提示词 | Agent/Memory提示词 | 所有抽取类提示词 |
| **迭代策略** | Refine保守更新 | Refine强制响应 | Gleaning多轮抽取 |
| **输出格式** | 自然语言为主 | JSON/结构化输出 | 自定义分隔符格式 |
| **多语言支持** | 手动翻译替换 | Hub多语言变体 | 语言参数配置 |
| **自定义方式** | update_prompts() | Hub版本管理 | settings.yaml配置 |

三个框架展现了RAG系统提示词设计的演进方向：从简单的问答模板（LlamaIndex）到可组合的Agent系统（LangChain），再到面向知识图谱的结构化抽取（GraphRAG）。LangGraph代表了最新趋势——放弃隐式默认，要求开发者显式定义每个提示词，以获得最大的控制力和透明度。

## 结论与最佳实践

本次逆向工程揭示了RAG框架提示词设计的三个关键洞察：

**设计模式趋同**：尽管框架定位不同，但都采用了相似的核心模式——上下文注入、角色定义、行为约束规则、Few-shot示例。这表明这些模式已经成为LLM应用的最佳实践。

**结构化输出成为标准**：从LlamaIndex的Pydantic Program到LangChain的`with_structured_output`，再到GraphRAG的自定义分隔符格式，框架都在强化对LLM输出的结构化控制，以提高下游处理的可靠性。

**显式定义取代隐式默认**：LangGraph完全放弃默认提示词的设计代表了一种范式转变。对于生产环境，这意味着开发者需要投入更多精力设计和维护提示词，但也获得了更大的控制力和可观测性。

对于框架选型，建议根据应用场景选择：**问答系统首选LlamaIndex**（成熟的默认提示词）；**Agent系统首选LangGraph**（灵活的图结构）；**知识图谱应用首选GraphRAG**（专业的抽取提示词）。跨框架迁移时，需要特别关注提示词的差异，尤其是输出格式和变量命名约定。
