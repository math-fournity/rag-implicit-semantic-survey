## 第61章：Haystack 2.0架构深度解析

### 从1.x到2.0的架构革命

Haystack 2.0于**2024年3月**正式发布稳定版，当前最新版本为**v2.20.0**（2025年11月）。这不是一次渐进式升级，而是一次彻底的架构重构——甚至连包名都从`farm-haystack`更换为`haystack-ai`，以示决心。

核心变革体现在**图执行模型**的升级：1.x版本采用有向无环图（DAG），而2.0支持**有向图（含循环）**，这使得自校正RAG、Agent迭代等复杂场景成为可能。数据流模型也从"全局数据流"转向"精确数据流"——组件之间仅传递显式声明的数据，而非隐式传递整个上下文。

```python
# Haystack 1.x (隐式连接)
pipeline.add_node(retriever, name="Retriever", inputs=["Query"])
pipeline.add_node(reader, name="Reader", inputs=["Retriever"])

# Haystack 2.0 (显式连接)
pipeline.add_component("retriever", retriever)
pipeline.add_component("reader", reader)
pipeline.connect("retriever.documents", "reader.documents")  # 精确指定数据流
```

这种显式连接设计带来两个关键优势：**类型安全**（连接时即验证类型兼容性）和**可调试性**（数据流向一目了然）。Gartner在2024年将Haystack评为**AI Engineering Cool Vendor**，正是认可了这种生产级架构设计。

### @component装饰器与插槽机制

Haystack 2.0的组件协议通过`@component`装饰器实现，这是整个框架的核心抽象。源代码位于`haystack/core/component/component.py`，其设计遵循**协议优于继承**的原则：

```python
from haystack import component
from typing import List

@component
class MetadataEnricher:
    def __init__(self, default_source: str = "unknown"):
        self.default_source = default_source
    
    @component.output_types(documents=List[Document])
    def run(self, documents: List[Document], source: str = None):
        # 输入：run()参数自动成为输入插槽
        # 输出：通过装饰器声明，返回字典
        for doc in documents:
            doc.meta["source"] = source or self.default_source
        return {"documents": documents}
```

**输入插槽**有三种定义方式：`run()`方法参数（静态）、`set_input_type()`（单个动态）、`set_input_types()`（批量动态）。**输出插槽**通过`@component.output_types()`装饰器或`set_output_types()`方法定义。这种设计使得Pipeline在`connect()`时就能进行完整的类型验证，而非等到运行时才发现错误。

### Pipeline执行引擎的并行与循环

Pipeline执行引擎（`haystack/core/pipeline/pipeline.py`）采用**拓扑排序**确定执行顺序，并通过`AsyncPipeline`支持**并行分支执行**：

```python
from haystack.core.pipeline import AsyncPipeline

async_pipeline = AsyncPipeline()
async_pipeline.add_component("retriever1", bm25_retriever)
async_pipeline.add_component("retriever2", embedding_retriever)
async_pipeline.add_component("joiner", DocumentJoiner())

# 两个retriever并行执行，joiner等待两者完成
async_pipeline.connect("retriever1", "joiner")
async_pipeline.connect("retriever2", "joiner")

result = await async_pipeline.run_async(data, concurrency_limit=4)
```

循环控制通过`ConditionalRouter`组件实现，配合`max_runs_per_component`参数（默认**100次**）防止无限循环。框架定义了三类异常：`PipelineRuntimeError`（组件失败）、`PipelineMaxComponentRuns`（达到最大运行次数）、`PipelineComponentsBlockedError`（循环依赖）。

### RAG组件生态全景

Haystack的RAG组件生态按功能分为**9大类**，核心组件位于`haystack/components/`目录：

| 组件类别 | 代表组件 | 源码路径 |
|---------|---------|----------|
| **Embedders** | SentenceTransformersDocumentEmbedder | `embedders/` |
| **Retrievers** | InMemoryBM25Retriever, InMemoryEmbeddingRetriever | `retrievers/` |
| **Generators** | OpenAIGenerator, HuggingFaceLocalGenerator | `generators/` |
| **Rankers** | TransformersSimilarityRanker | `rankers/` |
| **Builders** | PromptBuilder, AnswerBuilder | `builders/` |
| **Routers** | ConditionalRouter, FileTypeRouter | `routers/` |
| **Joiners** | DocumentJoiner (concatenate/merge/RRF) | `joiners/` |

**DocumentStore抽象**是存储层核心（注意：它不是Pipeline组件，而是Retriever的依赖）。官方支持**10+向量数据库**：InMemory、Elasticsearch、Qdrant、Pinecone、Chroma、Weaviate、PgVector、MongoDB Atlas等。混合检索通过`DocumentJoiner`的`join_mode`参数实现，支持`concatenate`、`merge`、`reciprocal_rank_fusion`三种策略。

### 生产部署与可观测性

Haystack提供**Hayhooks**作为官方部署方案，支持REST API暴露Pipeline：

```bash
pip install hayhooks
hayhooks run --pipelines-dir ./pipelines
# POST http://localhost:1416/deploy 部署Pipeline
# POST http://localhost:1416/{pipeline_name}/run 调用Pipeline
```

Pipeline序列化支持YAML/JSON格式，通过`pipeline.dump("file.yaml")`导出、`Pipeline.load(file)`加载。可观测性集成OpenTelemetry、Langfuse、Traceloop等主流追踪框架。企业用户包括**Apple、NVIDIA、Airbus、Netflix、德国联邦科技部**等。

## 第62章：Microsoft Semantic Kernel深度解析

### "AI编排层"的设计哲学

Semantic Kernel定位为**轻量级AI编排SDK**，当前版本C# **1.68.0**、Python **1.39.0**。与LangChain的"链式调用"不同，SK采用**插件架构**——AI通过描述理解现有代码，然后调用它们完成任务。

```csharp
// C# Kernel配置
var builder = Kernel.CreateBuilder();
builder.AddAzureOpenAIChatCompletion(
    Environment.GetEnvironmentVariable("AZURE_OPENAI_DEPLOYMENT"),
    Environment.GetEnvironmentVariable("AZURE_OPENAI_ENDPOINT"),
    Environment.GetEnvironmentVariable("AZURE_OPENAI_API_KEY")
);
var kernel = builder.Build();
```

**Azure深度集成**是SK的核心优势：原生支持Azure OpenAI Service、Azure AI Search（向量搜索）、Azure AI Foundry部署、Microsoft Entra ID认证。对于已投资Microsoft生态的企业，这意味着**零摩擦集成**。

### 核心抽象：Kernel、Functions与Plugins

SK的抽象层设计围绕三个概念展开：

**Semantic Functions（提示函数）**通过目录结构或内联代码定义：
```
Plugins/
└── WriterPlugin/
    └── ShortPoem/
        ├── skprompt.txt    # 提示模板
        └── config.json      # 配置（temperature等）
```

**Native Functions（代码函数）**使用`[KernelFunction]`属性标记：
```csharp
public sealed class MenuPlugin
{
    [KernelFunction, Description("Provides a list of specials from the menu.")]
    public string GetSpecials() => "Special Soup: Clam Chowder";
    
    [KernelFunction, Description("Provides the price of the requested menu item.")]
    public string GetItemPrice([Description("The name of the menu item.")] string menuItem)
        => "$9.99";
}
```

**Plugins架构**支持四种来源：Native Code、Prompt Templates、OpenAPI Specifications（与Microsoft 365 Copilot兼容）、**Model Context Protocol (MCP)**。

### Planner系统的演进与弃用

**重要变更**：Stepwise Planner和Handlebars Planner已被**弃用并移除**。Microsoft官方推荐使用**Function Calling**替代：

```csharp
ChatCompletionAgent agent = new()
{
    Name = "SK-Assistant",
    Kernel = kernel,
    Arguments = new KernelArguments(new PromptExecutionSettings()
    {
        FunctionChoiceBehavior = FunctionChoiceBehavior.Auto()
    })
};
```

Function Calling的优势在于：原生集成到GPT-4、Claude、Gemini等主流模型，无需额外的规划提示词，**token消耗更低、可靠性更高**。历史上的Sequential Planner生成XML计划、Stepwise Planner采用MRKL架构，但这些方法在复杂场景下的失败率较高。

### Memory与RAG集成架构

SK的Memory系统由`SemanticTextMemory`协调embedding生成和向量存储：

```python
from semantic_kernel.memory import SemanticTextMemory
from semantic_kernel.connectors.memory.qdrant import QdrantMemoryStore

qdrant_store = QdrantMemoryStore(vector_size=1536, url="http://localhost", port=6333)
memory = SemanticTextMemory(storage=qdrant_store, embeddings_generator=embedding_service)
kernel.add_plugin(TextMemoryPlugin(memory), "TextMemoryPlugin")
```

官方支持的**Vector Store Connectors**包括：Azure AI Search、Elasticsearch、Qdrant、Pinecone、Chroma、Redis、PostgreSQL (pgvector)、Milvus、MongoDB、Weaviate、In-Memory。

对于复杂文档处理，Microsoft提供独立的**Kernel Memory (KM)**服务，支持PDF、Word、PowerPoint、图像OCR等多模态输入。

### AutoGen合并与Microsoft Agent Framework

**2025年10月**，Microsoft宣布Semantic Kernel与AutoGen深度融合，形成**Microsoft Agent Framework**：

> "Think of Microsoft Agent Framework as Semantic Kernel v2.0 — it's built by the same team!"

这一合并带来三个关键变化：
1. **统一多Agent编排**：融合AutoGen的Group Chat、Debate能力
2. **共享运行时**：Dapr + Orleans支持
3. **标准化协议**：MCP、A2A（Agent-to-Agent）、OpenAPI

**迁移策略**：SK v1.x将继续获得bug修复和安全更新，至少在Agent Framework GA后支持**一年**。现有项目可继续使用，新项目可评估Agent Framework Preview。企业采用案例包括**KPMG Clara AI、Commerzbank、BMW、Fujitsu**等。

## 第63章：RAGFlow与Dify对比分析

### RAGFlow：深度文档理解的RAG引擎

RAGFlow由InfiniFlow（英飞流）于**2024年4月1日**开源，当前版本**v0.23.1**，GitHub Stars突破**70,946**（2024年全年增长26,800 stars，排名第7）。其核心定位是**深度文档理解**——通过自研DeepDoc引擎实现复杂格式的精准解析。

**技术架构**采用Flask 3.0（同步路由）+ Quart 0.20（异步流式），而非社区常见的FastAPI：

| 层级 | 技术选型 |
|------|----------|
| 后端 | Python 3.10-3.12, Flask 3.0, Quart 0.20 |
| 前端 | React 18, UmiJS 4, TypeScript |
| 存储 | MySQL 8.0, Elasticsearch 8.11 / **Infinity** |
| 队列 | Redis 6+ (Valkey 8) |

**DeepDoc引擎**是RAGFlow的核心竞争力，包含三大视觉处理模块：
- **OCR**：文本检测与识别（ONNX模型）
- **布局分析（DLR）**：识别文本、标题、图像、表格区域
- **表格结构识别（TSR）**：检测行、列、合并单元格

PDF解析流程：pdfplumber读取 → 页面转图像 → OCR提取文本框 → 布局识别确定逻辑区块 → XGBoost模型决定文本连接。源码位于`deepdoc/parser/pdf_parser.py`。

**分块策略**提供**12种内置模板**：General、Q&A、Resume（企业版）、Manual、Table、Paper、Book、Laws、Presentation、Picture、One、Tag。v0.21.0起支持**Ingestion Pipeline**可视化编排数据摄取流程。高级功能包括RAPTOR（递归抽象摘要）、GraphRAG（知识图谱）、Late Chunking（先embedding后分块）。

**Infinity向量数据库**是InfiniFlow自研的AI原生数据库，特性包括：混合搜索（稠密/稀疏向量+全文）、**0.1ms查询延迟、15K QPS**、内置RRF和ColBERT重排序。通过环境变量`DOC_ENGINE`可切换Elasticsearch、OpenSearch、OceanBase。

### Dify：低代码LLMOps平台

Dify由LangGenius开发，**2023年3月**成立，当前版本**v1.10.0**，GitHub Stars达**119,000+**（行业第一梯队）。其定位是**Backend-as-a-Service + LLMOps**，强调低代码/无代码的可视化体验。

**技术架构**采用Flask后端 + Next.js前端：

| 层级 | 技术选型 |
|------|----------|
| 后端 | Python, Flask, SQLAlchemy |
| 前端 | Next.js (React), TypeScript (51.2%) |
| 数据库 | PostgreSQL, Redis, Weaviate |
| 包管理 | UV（v1.3.0起替代Poetry） |

**工作流引擎**是Dify的核心能力，支持**14+节点类型**：

| 节点类型 | 功能 | 源码路径 |
|----------|------|----------|
| LLM | 调用大语言模型 | `/api/core/workflow/nodes/llm/` |
| Knowledge Retrieval | 知识库检索 | `/api/core/workflow/nodes/knowledge_retrieval/` |
| Question Classifier | LLM驱动的问题分类 | - |
| If/Else | 条件分支 | - |
| Code | Python/Node.js代码执行 | - |
| HTTP Request | 外部API调用 | - |
| Agent | 自主推理Agent | - |
| Iteration | 列表循环处理 | - |

工作流执行采用**队列化图执行模型**，数据库写操作异步非阻塞，执行时间接近最长分支时长。变量系统支持Jinja2模板语法。

**RAG管道**配置灵活：支持Vector Search、Keyword/BM25、Hybrid Retrieval、Reranking（Cohere Rerank）、Metadata Filtering（v1.1.0+）。知识库支持PDF、Word、Markdown、HTML、CSV、图片等多种格式。v1.0引入**Knowledge Pipeline**可视化RAG数据处理管道。

**Agent支持**包括Function Calling Agent和ReAct Agent两种模式，**50+内置工具**（Google Search、DALL·E、WolframAlpha等），支持MCP协议标准化工具集成。

### 架构设计哲学的根本差异

| 维度 | RAGFlow | Dify |
|------|---------|------|
| **核心定位** | 深度文档理解的RAG引擎 | 全栈LLM应用开发平台 |
| **目标用户** | 需要高精度检索的技术团队 | 快速上线的产品团队、非技术用户 |
| **文档解析** | 自研DeepDoc（OCR+布局+表格识别） | 标准解析器 |
| **工作流** | RAG流程优化为主 | **完整可视化编排器** |
| **Agent支持** | 有限 | **原生Agent节点** |
| **检索精度** | **精细控制**，适合复杂语料 | 良好默认值，可调优 |
| **学习曲线** | 陡峭，需技术背景 | 平缓，**30分钟可部署原型** |
| **部署复杂度** | 较高，资源需求大 | 简单，Docker一键部署 |

**选型建议**：
- 选择**RAGFlow**：核心痛点是复杂PDF/表格解析、需要可解释的分块结果、对检索精度有极高要求
- 选择**Dify**：需要快速验证想法、非技术团队参与、需要完整的前后端解决方案

## 结论

企业级RAG框架的选择本质上是**架构复杂度与业务灵活性的权衡**。Haystack 2.0的组件协议为生产级系统提供了坚实基础；Semantic Kernel的Azure深度集成使其成为Microsoft生态的不二之选；RAGFlow的DeepDoc引擎解决了复杂文档解析这一行业痛点；Dify的低代码理念则大幅降低了AI应用开发门槛。

关键洞察：**没有"最好"的框架，只有最适合特定场景的选择**。对于需要处理大量复杂PDF/表格的金融、法律、医疗行业，RAGFlow的深度文档理解能力是不可替代的；对于追求快速迭代的互联网团队，Dify的可视化编排可将开发周期从周缩短到天；对于已深度投资Microsoft生态的企业，Semantic Kernel（及即将到来的Agent Framework）提供了最低摩擦的集成路径；而对于需要完全可控的生产级部署，Haystack的显式架构和企业支持是稳健之选。

混合策略同样可行：Dify前端 + RAGFlow检索后端、Haystack管道 + 专业向量数据库——框架边界正在模糊化，**能力组合**才是未来趋势。
